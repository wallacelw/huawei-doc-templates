== Background

The customer currently runs a three-tier web application on an on-premises virtualization platform. The application consists of a frontend web layer, an application server layer, and a database layer. Peak traffic occurs during business hours, with predictable batch processing overnight.

The on-premises infrastructure is reaching end of life. The customer has selected Huawei Cloud as the target platform and wants to validate that the cloud services can support the application's performance and availability requirements before committing to a full migration.

== Goal and Objectives

[.objective]
Migrate the three-tier web application to Huawei Cloud and validate that the target architecture meets performance, availability, and security requirements equivalent to or better than the current on-premises deployment.

Specific objectives:

* Deploy the application on Huawei Cloud using CCE (Cloud Container Engine), RDS (Relational Database Service), and OBS (Object Storage Service).
* Validate that the application handles the expected peak load of 10,000 concurrent users.
* Confirm that automated failover and recovery work as designed.
* Verify that security controls (IAM, security groups, KMS) meet the customer's compliance requirements.
* Demonstrate end-to-end monitoring and alerting using Cloud Eye Service (CES).

== Solution Overview

=== Application Architecture

The application consists of three tiers:

* **Web tier:** Nginx serving static content and reverse-proxying to the application tier. Deployed on CCE with auto-scaling.
* **Application tier:** Java Spring Boot application running in containers on CCE. Connects to RDS for transactional data and OBS for file storage.
* **Database tier:** RDS for MySQL with a primary/standby configuration for high availability.

=== Target Cloud Architecture

The target architecture on Huawei Cloud includes the following components:

[.hutable]
|===
| Component | Service | Purpose

| Load Balancer | ELB (Elastic Load Balance) | Distributes traffic across web tier nodes
| Web Tier | CCE (Cloud Container Engine) | Containerized Nginx with auto-scaling
| App Tier | CCE (Cloud Container Engine) | Containerized Spring Boot application
| Database | RDS for MySQL | Primary/standby HA configuration
| File Storage | OBS (Object Storage Service) | Static assets and uploaded files
| Identity | IAM | User management and access control
| Encryption | KMS (Key Management Service) | Encryption key management
| Monitoring | CES (Cloud Eye Service) | Metrics, alarms, and dashboards
| Container Registry | SWR (Software Repository for Containers) | Container image storage and management
|===

== Scope

[.hutable]
|===
| Domain | What Will Be Tested

| Compute | CCE cluster creation, node scaling, container deployment
| Storage | OBS bucket creation, file upload/download, lifecycle policies
| Database | RDS instance creation, failover, backup and restore
| Networking | VPC configuration, subnet design, ELB setup, security groups
| Security | IAM policies, KMS key usage, encrypted storage
| Monitoring | CES dashboards, alarm rules, notification channels
|===

Out of scope:

* Data migration from the on-premises database (handled in a separate phase).
* Application code changes or refactoring.
* Disaster recovery across regions (validated in a later PoC).

== Premises and Preparation

* The customer has an active Huawei Cloud account with sufficient quotas for CCE, RDS, and OBS resources.
* The application container images are available in SWR (Software Repository for Containers).
* The customer has provided a representative test dataset (sanitized and anonymized).
* Network connectivity between the customer environment and Huawei Cloud is established via VPN.
* The Huawei Cloud team has access to the console and API endpoints for the target region.

=== Conclusion Criteria

The PoC will be considered successful when:

* All critical activities are classified as Pass or Partial without material risk.
* The application handles 10,000 concurrent users with response time under 200ms (p95).
* Automated failover completes within 30 seconds.
* Security controls meet the customer's compliance checklist.

NOTE: Verbal declaration or commercial presentation alone must not be considered proof. Functionality should be executed by the team in the PoC environment and its result registered.

== Comments and Remarks

* The load test results exceeded expectations — the target was 200ms p95 response time, and the actual was 189ms.
* Failover time of 22 seconds is well within the 30-second target.
* Monitoring validation was partial because the CES dashboard for database metrics requires a custom plugin that was not available during the PoC. This is a known limitation that will be addressed in the production deployment.
* No security issues were identified during the PoC. All storage is encrypted, IAM policies follow least-privilege, and security groups restrict access appropriately.
